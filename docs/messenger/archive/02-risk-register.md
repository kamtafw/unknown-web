# Messenger Web — Risk Register

Cross-cutting risks that affect more than one feature. Per-feature risks live in `01-scope-matrix.md`.

| # | Risk | Evidence | Impact if ignored | Action |
|---|---|---|---|---|
| 1 | **Socket auth vs. httpOnly cookies** | Token lives in `ac_token` httpOnly cookie (`lib/cookies.ts`); client JS can't read it; mobile puts the token directly in the socket connection because it can read it from `expo-secure-store`. | Realtime simply doesn't work — this blocks typing, delivery/read, group events, calls, Live. | **Updated after M0 kickoff:** no longer blocks *feature development* — ADR-003 implements a clearly-marked temporary dev mechanism (query-param token via `GET /api/messenger/socket-credential`) behind the `socketAuthProvider` abstraction. **Still open as a production architecture risk** — cookie-based auth vs. short-lived ticket has not been confirmed by backend, and the temporary mechanism must not ship as the final answer. Owner: confirm with backend before M0 is called fully closed. |
| 2 | **Socket consolidation assumption unverified** | Mobile runs 3 separate `io()` connections (chat/call/live) against the same host with 3 different auth shapes; guide recommends exactly one socket per session. | Building one consolidated connection on an untested assumption could mean call/Live events silently never arrive. | `lib/messenger/socket-manager.ts` implements the single-connection hypothesis behind an abstraction (ADR-002). **Partially confirmed 2026-08-11:** `scripts/messenger-socket-smoke-test.mjs` run against the real `socket.appscombo.com` — temporary auth (ADR-003) accepted, connection held open, `chat:typing` emitted without incident. **Still open:** group event round-trip (`group:join`→`group:error`/`group:message`) not yet exercised — needs a real `--group-id`; call/live namespaces untested (event names not documented until M8/M11). Don't treat this risk as closed until the group round-trip result comes back. |
| 3 | **AI moderation approve/decline likely doesn't exist on the backend** | Only a read-only spam-listing endpoint found; no approve/decline mutation, no pre-send violation-check anywhere in mobile code. | Building UI against an endpoint that doesn't exist wastes real time in a 2-week window. | Confirm with backend/PM before starting the approve/decline flow. Spam-tab listing is safe to build now regardless. |
| 4 | **Communities "access level hierarchy" has no confirmed data model** | Jira explicitly describes Level 1/Level 2 group access levels within a community; no matching field found in the traced community/group types. | Designing a hierarchy UI around an invented field structure means throwing it away later. | Check a live `GET chats/communities/:id` (or equivalent) response, or ask backend directly, before designing this UI. |
| 5 | **Status like/comment has no backend evidence** | Zero matches for like/comment anywhere in `use-status.ts` or the status viewer screen, despite being explicit Jira acceptance criteria. | Same as #3/#4 — real risk of building against a non-existent contract. | Confirm with backend/PM. Reshare (exists) can ship; like/comment stays Blocked until confirmed. |
| 6 | **Calling + Live are the two largest undocumented surfaces in the project** | `use-call-signaling.ts` alone is 3,379 lines with zero guide coverage; `use-live.ts` is 786 lines, also undocumented. | Underestimating these two features is the single biggest threat to the 2-week timeline — not because porting WebRTC to browser is exotic, but because the *business logic* (ringing, ICE renegotiation, mic-request approval, co-host promotion) has to be reverse-engineered from scratch. | Treat signaling reverse-engineering as its own scoped step (Milestone 8) with a written contract as the deliverable, before any call/Live UI is built. |
| 7 | **Peer-mesh WebRTC, no SFU found** | `peer-connection.ts` only configures STUN (Google/Cloudflare) + TURN (Metered) — no media server. | Group calls and Live sessions with more than a handful of active speakers won't perform well; this is inherited from the existing product, not a web engineering gap. | Set expectations explicitly with the client: "group calling/Live works well for small groups, consistent with the existing mobile app" rather than promising unlimited scale. Don't silently redesign the backend's media architecture. |
| 8 | **Multiple browser tabs** | Guide explicitly flags this as a web-specific problem mobile doesn't have. | Duplicate sockets, duplicate notification sounds, duplicate optimistic sends across tabs. | Single-tab-owns-socket election or `BroadcastChannel` relay — part of Foundation, not an afterthought. |
| 9 | **UUID vs. PKID confusion** | Guide's own top-listed risk; confirmed real in code (`chats/history/:userUuid` vs. `receiver_id` as PKID in the same feature). | Silent wrong-recipient bugs, broken history lookups. | Enforce in types: never a bare `userId`, always `userUuid` / `userPkid` in function signatures and DTOs. |
| 10 | **Inconsistent endpoint prefixes** | Some endpoints use `messenger/...` (`messenger/conversations/:id`, `messenger/groups/:id`, `messenger/calls/:id/end`, `messenger/live/:id/viewers`) alongside the primary `chats/...` / `calls/...` / `live/...` prefix. | Picking the wrong prefix silently 404s or hits a different (possibly legacy/admin) route. | Confirm which prefix is canonical per operation before wiring the BFF proxy for it — don't assume `chats/...` is always right just because it's more common. |
| 11 | **Notification API browser support gap** | "Call Now / Decline" scheduled-call notifications rely on native action buttons on mobile (OneSignal); Safari doesn't support Notification API action buttons. | Feature silently degrades or breaks on Safari specifically. | Design an explicit fallback (click notification → open reminder screen with the same actions) rather than assuming action buttons work everywhere. |
| 12 | **E2EE must not be implied** | Guide states encryption is non-functional on mobile today; `lib/crypto/*` exists on mobile only, not web. | Claiming encrypted messaging that isn't real is a trust/legal problem, not just a bug. | Don't build or message anything about E2EE in this pass; revisit only if product explicitly commits to the full protocol + key lifecycle + review. |

## Reading this register going forward

Risks #1–#5 are **blockers to specific milestones**, not general caution — each has a concrete "who do I need to ask, and what happens if I don't" attached. Risks #6–#12 are **standing engineering discipline** that should be checked at the end of every milestone, not just once.
